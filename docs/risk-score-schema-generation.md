# RiskScore Cross-Repo Schema/Type Generation (Spike)

Date: 2026-08-30
Branch: `evaluate-riskscore-type-generation-932`
Status: Spike complete — recommendation below is ready for an ADR / implementation follow-up.

## Summary

`RiskScore` is defined once in Rust
(`contracts/ledgerlens-score/src/types.rs`) and today every downstream consumer
re-mirrors it by hand: TypeScript and Python SDKs, the dashboard, and the API
each maintain their own copy of the field set, order, and the `[0, 10^2]` score
domain.

This spike proves that the **Soroban contract-spec (XDR)** is a single,
machine-readable source of truth that can generate a JSON Schema plus one or
more language bindings with zero changes to the contract crate's behavior or
WASM size.

**Recommendation:** generate bindings from the Soroban contract-spec — reading
the *native* `RiskScore::spec_xdr()` for local regeneration, or the
`contractspecv0` section of a deployed WASM for post-deploy consumers — layer
the semantic ranges on top from the contract's own `constants`, and commit the
generated artifacts (with a CI drift check) rather than publishing a package.
Adopt this approach across api, dashboard, and both SDKs.

## Approaches compared

| | **A. Soroban contract-spec (XDR)** ✅ | B. `schemars` derive on the contract struct | C. `ts-rs` / `typeshare` | D. Hand-authored manifest/schema |
| --- | --- | --- | --- | --- |
| Source of truth | The real compiled spec (`#[contracttype]` already emits it) | An added derive on the existing struct | An added derive/annotation on the existing struct | A 4th copy maintained by humans |
| Contract crate changes | None required | New dependency + attribute on the struct | New dependency + attribute on the struct | None, but the copy *is* the problem |
| WASM size impact | None (spec already compiled in) | Adds schemars (large) and JSON blobs to the token | None at build time, but must be kept in sync manually (orphan rule → edits land in the contract crate anyway) | None |
| Cross-language output | JSON Schema + TS + Python (PoC proves all three) | JSON Schema (TS/Python via schema typing tooling) | TS only (typeshare); another tool needed for Python/JS | Whatever you hand-write |
| Works from a deployed WASM (no source checkout) | ✅ `soroban_spec::read::from_wasm`, same read path Soroban's typed-client generators use | ❌ | ❌ | ❌ |
| Fidelity to real field set/order | Byte-exact: generated from the same XDR bytes the on-chain spec is built from | Whatever you maintain on the derive | Whatever you maintain on the annotate | Whatever you maintain by hand |
| Drift safety | `--check` compares regenerated bytes against committed artifacts | Schema validation testing | Type mismatch | Manual |

**Schemars** is the strongest runner-up for pure Rust->JSON-Schema, but it
requires adding a large dependency + derive to the production contract (with
WASM-budget implications, see `docs/wasm-size-budget.md`) and it cannot speak
for any artifact that wasn't built from the current source. The XDR approach
reads the *exact bytes the contract ships with*, which is strictly more
authoritative.

## Proof of concept

New workspace crate `tools/schema-gen` implements option A end to end.

### Generation pathways

```text
cargo run -p schema-gen                         # native: RiskScore::spec_xdr()
cargo run -p schema-gen -- --wasm target/wasm32-unknown-unknown/release/ledgerlens_score.wasm
cargo run -p schema-gen -- --out schemas/       # emit elsewhere
cargo run -p schema-gen -- --check              # CI drift gate (exit non-zero if stale)
```

Outputs (committed, in `schemas/`):

| Artifact | Consumers |
| --- | --- |
| `schemas/risk_score.schema.json` (draft-07) | api validation, fixture checking, any schema-tooling |
| `schemas/risk_score.ts` | TypeScript SDK, dashboard |
| `schemas/risk_score.py` (Pydantic v2) | Python SDK |

### How the output is genuinely derived (not hand-copied)

- **Field names, types, and count** come from the XDR struct spec generated by
  the `#[contracttype]` derive — the same bytes stored in the contract's
  `contractspecv0` section. `native_risk_score_struct()` decodes
  `RiskScore::spec_xdr()`; `wasm_risk_score_struct()` uses
  `soroban_spec::read::from_wasm`.
- **Numeric domain** is sourced from `ledgerlens_score::constants::{MIN_SCORE,
  MAX_SCORE}` (made `pub` for this purpose; the only contract-crate change, 4
  comment lines). `score`, `confidence`, `benford_score`, `ml_score`,
  `network_score` all emit `minimum: 0`, `maximum: 100` straight from those
  constants. `model_version`/`timestamp` get only `minimum: 0` (unsigned) and
  no semantic max, because the contract imposes none.
- **Order** is contract-spec order. Verified fact: the `#[contracttype]` derive
  sorts struct fields *alphabetically by name*
  (`derive_struct.rs` `sorted_by_key(|f| f.ident...)`), not Rust declaration
  order. All three artifacts therefore list `benford_flag, benford_score,
  commitment, confidence, ml_flag, ml_score, model_version, network_score,
  score, timestamp`. This is also the order the existing historical-WASM golden
  and on-chain decoders use.
- **Nullability** follows the Rust type: `Option<Bytes>` (`commitment`)
  emits `anyOf [string(base64)]/null` in JSON Schema, `string | null` in TS, and
  `Optional[str] = None` in Python.

## Fidelity and gaps of the XDR source

The contract-spec is the authoritative *shape and type* source, but it is not a
documentation or semantics source on its own:

- XDR carries no field-level docs and no numeric ranges, so constraints must be
  layered from the contract's own `constants.rs` (as this PoC does) or a small
  mapping. This PoC keys the `[0,100]` domain by field name.
- Gap to promote (follow-up): only `score` has a named constant today;
  `confidence`, `benford_score`, `ml_score`, `network_score` have
  *no named constants* even though the contract enforces the same domain on
  them. Adding named constants in `constants.rs` would let the generator key
  off them 1:1 instead of a name map.
- `Bytes`/`BytesN` are emitted as base64 `string` with
  `contentEncoding`/`minLength`/`maxLength` (draft-07 compatible); the `+`/
  `/` vs URL-safe Base64 detail is a downstream convention decision, not a
  schema decision.

## Distribution recommendation

1. **Commit the generated artifacts** in this repo under `schemas/` with
   embedded provenance headers.
2. **Add a CI drift gate**: run `cargo run -p schema-gen -- --check` in CI so
   any `types.rs`/`constants.rs` change that would silently desync consumers
   fails the build with a regenerate message. This is the analogue of the
   existing historical-WASM goldens.
3. **Consume, don't copy**: reference the JSON Schema file directly (or export
   it to the internal registry) from api for payload validation; generate
   `risk_score.ts`/`risk_score.py` into the SDKs' repos from this repo's
   regenerated artifacts (copying the *generated output* — never the Rust
   struct — keeps a single write-side source of truth).
4. Optional later step: promote the generator loop into the shared GitHub
   Actions workflow so a merge in `contracts/ledgerlens-score` auto-regenerates
   and opens sync PRs in the consumer repos. See follow-ups.

## Interaction with `sdk_conformance_fixtures.json`

`tests/composability/sdk_conformance_fixtures.json` is a **behavioral,
gate-level** fixture: each case is `(score, confidence, age_secs) -> expected
gate outcome`, where `score`/`confidence` are nullable signals *into* the gate,
not full `RiskScore` payloads. It therefore is **not** validated by the
`RiskScore` JSON Schema, and humans should not try to make it so.

- Where the fixture overlaps (the non-null `score`/`confidence` values all lying
  in `[0,100]`, verified against the generated schema), the generated schema can
  guard the fixture at authoring time.
- The fixture's *shape/decoding* could eventually be generated or
  schema-validated too, but its *expected outcomes and null-handling cases*
  must stay hand-authored — they encode product policy, not types.
- So the generated schema **complements** the fixture (type/domain authority)
  rather than replacing it (behavior authority). Update
  `docs/sdk-conformance-fixtures.md` only if this relationship needs
  documenting for SDK maintainers.
